# Changelog

All notable changes to this project will be documented in this file.

## [Unreleased]

### What this release does not fix
- **Some commands the bundled scanner prints still name a command that does not run.** `opena2a-cli` installs only the `opena2a` bin, so a citation of `hackmyagent <verb>` is not on PATH. Two kinds remain. (1) Strings the scanner writes with `hackmyagent` fixed in the text instead of the prefix opena2a sets: `Run: hackmyagent nanomind setup`, which `opena2a check <dir> --nanomind` prints on standard error; `hackmyagent harden-soul .` in governance findings; `Verify: hackmyagent secure ...` in NanoMind fix text; `No backup found. Run hackmyagent secure --fix <dir> first` from `opena2a rollback`. opena2a rewrites citations in standard output only, and never inside `--json` or `--format json|sarif` output, which carries the scanner's strings as the scanner wrote them. `hackmyagent harden-soul` is not rewritten to `opena2a harden-soul` on purpose: the opena2a command takes no backup before it writes and exits 0 when the write is refused, so it is a different command. (2) Verbs the scanner prints under the `opena2a` prefix that opena2a does not register: `attack` (also in the next steps of `opena2a check <package>`), `check-metadata`, `explain`, `init-mcp`, `pull-stubs`, `red-team`, `secure-nemoclaw`, `secure-openclaw` and `wild`. Both are fixed in the scanner, not here; `packages/cli/__tests__/cited-engine-verbs.test.ts` lists the verbs in (2) and fails when the scanner cites a verb that is neither registered nor listed. **Verify:** while the NanoMind daemon is not set up, `opena2a check <dir> --nanomind 2>&1 | grep -n 'nanomind setup'` prints the standard-error line with `hackmyagent`. **Fix:** type `opena2a nanomind setup` for `hackmyagent nanomind setup`, and `opena2a scan` with the same arguments (`--fix` included) for `hackmyagent secure`; for `hackmyagent harden-soul .`, `npx hackmyagent harden-soul .` runs the scanner's own command, which backs up first.
- **A tree-local package-manager configuration runs before the CLI's first instruction.** A committed `.npmrc` carrying a `node-options` line is read by npm itself whenever the CLI is started through `npx`, `npm exec` or `npm run` inside that tree, and the options it names take effect before the CLI's first instruction. Yarn's `.yarnrc` and `.yarnrc.yml` and pnpm's `.pnpmfile.cjs` are the same class for those package managers. No in-process check can detect it: by the time any opena2a-cli code executes, the code that configuration loaded has already run and could have altered anything a check would look at. This is a permanent limit of starting the CLI through a package manager from inside the tree it is pointed at, not a defect a later release can close. **Verify in a tree you are about to scan:** `find <tree> -name node_modules -prune -o \( -name .npmrc -o -name .yarnrc -o -name .yarnrc.yml -o -name .pnpmfile.cjs \) -print` prints each such file; treat anything it prints as code that runs when a package manager is invoked inside that tree. **Fix:** start the CLI from outside the tree and name the target as an operand, for example `npx opena2a-cli review "$GITHUB_WORKSPACE"` with `working-directory: ${{ runner.temp }}` in a GitHub Actions step; the `opena2a-cli` recipes in `docs/use-cases/ci-cd.md` for GitHub Actions, GitLab CI, Azure Pipelines and CircleCI take this form. Do this whichever way the CLI is installed: the scanner runs the CLI delegates to are started from the directory you run `opena2a` in, some of them through `npx`, and this release does not change that. Every documented `npx opena2a-cli` line for one of the fifteen commands the docs test enforces (`init`, `protect`, `review`, `status`, `detect`, `setup`, `runtime`, `scan-soul`, `harden-soul`, `harden-skill`, `benchmark`, `comply`, `check`, `trust` and `claim`) now names its target, and that test, `packages/cli/__tests__/repo/docs-npx-explicit-target.test.ts`, fails `npm run test` when one of those lines stops doing so. This repository's own CI and release build jobs refuse to install while any of these files, or an `.envrc`, is tracked; that protects this project's builds and does nothing for a tree you scan.

### Added
- `opena2a review --format json` carries four more facts. `hmaData.run` says how the HMA scan ended: `status` is `ran`, `skipped`, `notFound`, `timedOut`, `badOutput` or `exitError`; `reason` is one line on why there is no result, null when the scan ran; `version` is the first line `hackmyagent --version` printed; `durationMs` is how long the phase took. A URL password, or a value the credential catalog recognises, in `reason` or `version` is replaced with `[redacted]`. `initData.envFiles` lists the env files found in the tree, each with the number of lines that assign a value, whether git ignores or tracks it, whether `git add .` would stage it, and its mode; the values themselves are never read into the report. `credentialData.coverage` gives the number of files the credential scan read (`filesRead`), the matches it dropped as published examples or placeholders (`placeholdersSkipped`) and the folders it did not enter (`skippedDirs`). `guardData.candidates` lists the files a bare `opena2a guard sign` would sign in the reviewed directory.
- `opena2a telemetry status` prints a `contributor_token:` line under `install_id:`. Scans the CLI contributes to the Registry's community trust data carry this token and no install ID, so it is the value that identifies them there; the install ID does not. The token is derived on this machine from a random salt kept at `~/.opena2a/contributor-salt` together with the host and user name, and is the same token every contribution from this machine and user sends. If no salt exists yet, the command creates it. `opena2a telemetry on` and `off` print the same line.
- `OPENA2A_ADVISORIES=off` makes `opena2a review` and `opena2a init` skip the advisory request (#464). Both commands read the Registry's advisory list by default and wait up to 5 seconds for it; the request names a date and a count and nothing about the project, and dependencies are matched on this machine. With the variable set, no request is made, the advisories are reported as not checked, and the report says how to turn the check back on. The command reference (`docs/commands.md`) and `opena2a --help` describe the request.

### Fixed
- `opena2a watch` exits 0 when it is stopped with Ctrl+C the moment its banner appears. It printed `Polling every 3s (Ctrl+C to stop)` before it started handling Ctrl+C, so an interrupt that arrived between the two, as one sent by a script that waits for that line does, ended the process by the signal's default action (status 130 in a shell) and printed no `Stopped watching.` line, where `watch --help` says Ctrl+C exits 0. The SIGINT and SIGTERM handlers are now installed before anything is printed, with or without `--json`; the output, the polling and the exit codes are otherwise unchanged. `packages/cli/__tests__/commands/watch-ctrl-c.test.ts` checks that both handlers are in place when the `Ctrl+C to stop` line is written and that an interrupt at that moment returns 0, and the `watch` case of `packages/cli/__tests__/util/help-contract-exec.test.ts` sends SIGINT to the built CLI as soon as that line appears and requires exit 0.
- `opena2a benchmark` no longer prints a rating for a target it could not scan. Given a directory that does not exist, it printed `Rating: Partial` and `L1: 100% (3 of 39 controls evaluated)` and exited 0, so a CI step with a mistyped path passed. A target that does not exist, is not a directory or cannot be read is now refused before any scan: stderr reads `opena2a benchmark: <target> does not exist, so nothing was scanned.` (or `is not a directory`, or `could not be read`) followed by `  Verify: ls -ld <target>`, nothing is written to stdout, including under `--format json`, and the command exits 2 with or without `--ci`. The target is shown resolved, in one form on both lines: bare when it holds only ASCII letters, digits and `_./-`, and otherwise single-quoted, so the Verify line pastes as printed. A target holding a character that `@opena2a/cli-ui` escapes, such as a control character, a bidi control, a zero-width character or a line separator, is instead shown as `$'...'` with each such character escaped (`\e`, `\u202e`, `\u200b`), never raw, and its Verify line reads `  Verify: ls -ld <dir>`, because not every shell reads that rendering back as the same path. An existing directory with nothing to scan still reads `100% (3 of 39 controls evaluated)`, because the three credential controls are counted as evaluated before any file is read; that is not changed here.

The file locations listed under each finding stay relative to the scanned directory. In the scope drift callout for DRIFT-001 and DRIFT-002, `Verify:` named `opena2a protect`, which applies fixes; it is now `opena2a protect --dry-run`, which runs the live access check and reports drift without changing a file, and `Fix:` is `opena2a protect`. The callout also said the dry run made no live API check; it makes one unless `--skip-liveness` is given, and the line now says so. The `opena2a` commands printed as a Fix (`opena2a protect`, `opena2a shield init`, `opena2a guard sign`) still name no directory and act on the one they are run in. **Verify:** from the parent of a project directory, every `Verify:` line `opena2a init <project>` prints names its file under `<project>/` and runs there. It said every `.key`, `.pem`, `.p12` or `.pfx` file was "checked into source" whether git tracked it or not, and a key git did not track (a repository with no commit, an ignored file, or no repository) got a `Verify:` line and no `Fix:` line. - `opena2a review` verifies the Shield event log's hash chain before it trusts the events in it (#204). - Two `opena2a` processes writing an event at the same time no longer fork the Shield event log. `writeEvent` read the last line for its `prevHash` and then appended, with nothing serialising the two steps, so interleaved writers appended two events claiming the same predecessor. Measured on a fresh log with 8 concurrent writer processes: `{"valid":false,"brokenAt":1}` on 5 of 5 runs, and 7 of 10 runs at 2 writers. No attacker involved — a shell preexec hook firing while `opena2a` runs, or a git hook racing a CI step, is enough. That fork used to be cosmetic; now that `review` verifies the chain, it produces a `critical` finding, a "Not safe to ship" verdict, exit 1, and the permanent exclusion of every later event, on a clean project. The read-and-append sequence (and the size-based rotation that can rename the file underneath it) now runs under an `O_EXCL` lockfile with a synchronous wait. A lock whose recorded pid is dead on this host, or that is older than 5s, is taken over; the 6s acquisition timeout deliberately exceeds that staleness window so an abandoned lock is always reclaimed rather than outliving every waiter. On a genuine timeout the event is still written — losing a security event is worse than a forked chain — but never silently: stderr names the lock, the holder's pid and host, and the wait. `O_EXCL` is atomic locally and not reliable on NFS, so a network-mounted home degrades to the age rule.

The new event was lost with the fragment, and every later event chained off genesis in the middle of the file, so `review` reported a critical `SHIELD-INT-002` and excluded every genuine event after the tear. The writer now links to the last valid event, skipping the torn line exactly as the reader does, and starts the new event on its own line. ### Security
- **`opena2a review` no longer writes detected credential values into its reports.** `credentialData.matches[].value` carried each detected secret verbatim, in `--json` output and in the payload embedded in the HTML report, while the HTML page itself showed a masked preview. The value is now masked where the phase data is built (3-character head, 2-character tail, the same mask `comply` uses), so every output format inherits it; `file:line`, finding id and severity are unchanged. The HTML report is written owner-only (`0600`) when it is created (#267).
- **Every child process opena2a-cli starts now receives a declared environment, never the operator's whole one.** Seven sites in shipped code spread `process.env` into a child: `packages/cli/src/index.ts` (the two direct `hackmyagent` spawns), `router.ts` (the `check` delegation), `shield/llm-backend.ts` (the `claude --print` call), and the `envInherit` branch of `adapters/spawn.ts`, `python.ts` and `docker.ts`. `commands/review.ts` passed no environment at all to its `npx hackmyagent secure`, which inherits the same way. The children are the delegated scanner and the local model CLI binary. Every release since each site appeared handed that child the operator's full environment — cloud credentials, registry tokens, database URLs, every API key in the shell — and 0.10.12, which narrowed the adapters' allowlisted path, recorded that these direct spawns still inherited.
