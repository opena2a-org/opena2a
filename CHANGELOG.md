# Changelog

All notable changes to this project will be documented in this file.

## [Unreleased]

### What this release does not fix
- **A tree-local package-manager configuration runs before the CLI's first instruction.** A committed `.npmrc` carrying a `node-options` line is read by npm itself whenever the CLI is started through `npx`, `npm exec` or `npm run` inside that tree, and the options it names take effect before the CLI's first instruction. Yarn's `.yarnrc` and `.yarnrc.yml` and pnpm's `.pnpmfile.cjs` are the same class for those package managers. No in-process check can detect it: by the time any opena2a-cli code executes, the code that configuration loaded has already run and could have altered anything a check would look at. This is a permanent limit of starting the CLI through a package manager from inside the tree it is pointed at, not a defect a later release can close. **Verify in a tree you are about to scan:** `find <tree> -name node_modules -prune -o \( -name .npmrc -o -name .yarnrc -o -name .yarnrc.yml -o -name .pnpmfile.cjs \) -print` prints each such file; treat anything it prints as code that runs when a package manager is invoked inside that tree. **Fix:** start the CLI from outside the tree and name the target as an operand, for example `npx opena2a-cli review "$GITHUB_WORKSPACE"` with `working-directory: ${{ runner.temp }}` in a GitHub Actions step; the `opena2a-cli` recipes in `docs/use-cases/ci-cd.md` for GitHub Actions, GitLab CI, Azure Pipelines and CircleCI take this form. Do this whichever way the CLI is installed: the scanner runs the CLI delegates to are started from the directory you run `opena2a` in, some of them through `npx`, and this release does not change that. Every documented `npx opena2a-cli` line for one of the fifteen commands the docs test enforces (`init`, `protect`, `review`, `status`, `detect`, `setup`, `runtime`, `scan-soul`, `harden-soul`, `harden-skill`, `benchmark`, `comply`, `check`, `trust` and `claim`) now names its target, and that test, `packages/cli/__tests__/repo/docs-npx-explicit-target.test.ts`, fails `npm run test` when one of those lines stops doing so. This repository's own CI and release build jobs refuse to install while any of these files, or an `.envrc`, is tracked; that protects this project's builds and does nothing for a tree you scan.

### Added
- `opena2a review --format json` carries four more facts. `hmaData.run` says how the HMA scan ended: `status` is `ran`, `skipped`, `notFound`, `timedOut`, `badOutput` or `exitError`; `reason` is one line on why there is no result, null when the scan ran; `version` is the first line `hackmyagent --version` printed; `durationMs` is how long the phase took. A URL password, or a value the credential catalog recognises, in `reason` or `version` is replaced with `[redacted]`. `initData.envFiles` lists the env files found in the tree, each with the number of lines that assign a value, whether git ignores or tracks it, whether `git add .` would stage it, and its mode; the values themselves are never read into the report. `credentialData.coverage` gives the number of files the credential scan read (`filesRead`), the matches it dropped as published examples or placeholders (`placeholdersSkipped`) and the folders it did not enter (`skippedDirs`). `guardData.candidates` lists the files a bare `opena2a guard sign` would sign in the reviewed directory.
- `opena2a telemetry status` prints a `contributor_token:` line under `install_id:`. Scans the CLI contributes to the Registry's community trust data carry this token and no install ID, so it is the value that identifies them there; the install ID does not. The token is derived on this machine from a random salt kept at `~/.opena2a/contributor-salt` together with the host and user name, and is the same token every contribution from this machine and user sends. If no salt exists yet, the command creates it. `opena2a telemetry on` and `off` print the same line.

### Fixed
- `opena2a review` no longer names an HMA scan that timed out, failed or printed something other than a report as skipped or not installed. The progress line read `skipped`, the phase detail `Not installed`, and the provisional-verdict notice said to install hackmyagent, although the scan had started. The progress line now reads `timed out`, `failed` or `output unreadable`, the phase detail `Timed out`, `Scan failed` or `Output not readable`, and the notice says the deep scan produced no result, gives the reason, and after a timeout or a failure names `npx hackmyagent secure` on the reviewed directory as the way to see the scanner's own output. A scan skipped with `--skip-hma` reads as before in all three places. For a scan `npx` could not start, the progress line now reads `not installed`, where it read `skipped`; its phase detail (`Not installed`) and its notice (`Install it: npm i -g hackmyagent`) read as before.
- `opena2a identity revoke` no longer says that a revoked agent's data is kept for 30 days and then permanently deleted, and the `identity` help no longer describes `revoke` as permanently deleting the agent from the server. The 30-day period was a fixed value in the CLI, not something the server reported. The confirmation prompt now states only that the agent will be revoked, with the confirm command and `suspend` as the alternative, and after a revoke the CLI prints `opena2a identity reactivate --server cloud` as the way back. `identity revoke --json` no longer carries `retentionDays`: the key is removed, not set to null or 0. The object now carries the members of the server's revoke response under the server's own names, as `identity reactivate --json` already did, so any time value in it is one the server sent.
- The `opena2a review` HTML report no longer scrolls sideways at 375px wide because of its tab bar or a wide table, and its file-list toggles open from the keyboard. At 375px wide every tab scrolled sideways, to 518px and to 578px on Overview: the six-tab bar did not wrap and a five-column table set the page width. The tab bar now wraps, a table wider than the screen scrolls inside its own card, and long file paths and commands break inside their card. "+ N more files" was a `span` only a mouse could open; it is now a button that Tab reaches and Enter or Space opens, and it reports whether it is expanded. Focus moves to a tab opened from a button inside the page. A table that scrolls sideways is a Tab stop, so the arrow keys scroll it. The page width at 1280px is unchanged.
- `opena2a review` and `opena2a detect` tell a command error apart from a result (#383). `review` exited 1, the code for a score below 50, when its target directory did not exist and when a `--format text` run could not write its `--report` path; both now exit 2, the command-error code in the CI exit-code table, and the text run names the cause as `Report not written: ...` after the summary. `review` strips control characters from the `--format` value and the `--report` path before printing them, so a crafted value can no longer put an escape sequence or an extra line on the terminal. `detect --format json` printed its `Report: <path>` and `Asset inventory: <path>` confirmations on stdout after the JSON document, so adding `--report` or `--export-csv` broke a `jq` pipeline; under `--format json` they now go to stderr, and text output is unchanged. `detect --format sarif`, which the global `--format` help lists, printed the text audit and exited 0; `detect` produces no SARIF, so any format other than `text` or `json` now exits 2 before scanning, with a message naming the two it supports.
- A named pipe at `~/.opena2a/shield/events.jsonl` no longer blocks the Shield event-log reader that `opena2a review` and the `opena2a shield` commands share (#383). The reader opened the log before checking that it is a regular file, and opening a pipe with no writer waits for one, so the command never returned; the open is now non-blocking, and a pipe is refused as an unreadable log, as a directory already was.
- `opena2a skill create` no longer overwrites an existing skill and exits 0. Run against a directory that already holds files, it replaced `SKILL.md` and `index.ts` and reported success; it now refuses, names the directory, and exits 1 (JSON output: `{"error": "directory-not-empty", "directory": ...}`). `--force` replaces the scaffold files deliberately; an existing empty directory is still accepted. The `Next steps` hint now prints the directory actually written, so `--output` no longer yields a `cd <name>` that does not exist (#263).
- `opena2a shield report` reads the event log through the same hash-chain check as `opena2a review` (#243). It previously counted every line in `events.jsonl`, so forged criticals appended past a chain break inflated the severity breakdown, the SARIF output and the HTML and trend snapshots while `review` excluded them. Events at and after the first break now feed none of those; the break is reported once as `SHIELD-INT-002`, and the text, JSON (`logIntegrity`) and file-written outputs state how many events were excluded, with `opena2a shield selfcheck` to verify and `opena2a shield recover --archive-log` to start a fresh chain.
- An unregistered verb given with a flag no longer exits 0 as a different command. `opena2a fix-all --with-aim` reached the natural-language fallback, printed `Matched: opena2a identity` and exited 0; argv with a flag after the first token, or with a hyphenated first token, now goes to the command parser, which reports `unknown command 'fix-all'` and exits 1, as the positional form already did. Quoted phrases (`opena2a "..."`) are unchanged. `skill`, `harden-skill`, `harden-soul`, `scan-soul` and `telemetry` were registered but missing from the known-command list the fallback consults; a test now fails on that drift (#291).
- `opena2a runtime init` generated an `arp.yaml` whose `interceptors` and `aiLayer` blocks the ARP engine could not act on, and `opena2a runtime status` reported those detectors as configured anyway. The template wrote bare booleans (`process: true`) and the hyphenated `MonitorType` spellings (`mcp-protocol:`, `a2a-protocol:`); the engine reads `ic?.process?.enabled` and `al?.mcp?.enabled`, and `AILayerConfig` has no `mcp-protocol` key, so both resolve to `undefined`. Optional chaining on a boolean is silent, so nothing threw: the config file asserted protection that was never constructed. Measured against the shipped engine, the old template with every flag set to `true` builds `["filesystem","network","process"]` and nothing else. `status` hid it by hand-parsing the YAML line by line and truthy-checking the same bare booleans, printing `Interceptors: prompt, mcp-protocol, a2a-protocol` for a config that armed none of them. `init` now emits object blocks with an `enabled` field and the `mcp`/`a2a` keys, from a single helper (the template was duplicated across two functions and both were wrong), and ships the two in-process groups off with a pointer to the library path rather than arming detectors that can only see the CLI process. `status` parses with `js-yaml` and applies the engine's own predicates, and now also reads the `interceptors` block, which it ignored entirely. A regression test builds a real `AgentRuntimeProtection` from the generated file and asserts the detectors are constructed; the previous test asserted the string `mcp-protocol: true` was present, which is what let this ship.
- `opena2a review` verifies the Shield event log's hash chain before it trusts the events in it (#204). It used to classify every line of `~/.opena2a/shield/events.jsonl` as genuine, so an edited, inserted or removed event counted the same as a real one. `review` now reads the log through the chain verifier and classifies only the events before the first break; the break itself is reported as one critical `SHIELD-INT-002` finding. The excluded events are never shown as findings, but the Shield score takes the harsher of the score with and without them, so damaging the log can no longer improve the score. The terminal summary, a stderr notice and the HTML report's Shield tab state how many events were excluded and where the chain broke. With `--json`, the Shield phase is marked `provisional` and the Shield data carries `chainBroken`, `brokenAt` and `untrustedEventsExcluded`. The chain carries no key: it detects a damaged, edited, inserted or removed line, not a rewrite that recomputes every later hash.
- Two `opena2a` processes writing an event at the same time no longer fork the tamper-evident log. `writeEvent` read the last line for its `prevHash` and then appended, with nothing serialising the two steps, so interleaved writers appended two events claiming the same predecessor. Measured on a fresh log with 8 concurrent writer processes: `{"valid":false,"brokenAt":1}` on 5 of 5 runs, and 7 of 10 runs at 2 writers. No attacker involved — a shell preexec hook firing while `opena2a` runs, or a git hook racing a CI step, is enough. That fork used to be cosmetic; now that `review` verifies the chain, it produces a `critical` finding, a "Not safe to ship" verdict, exit 1, and the permanent exclusion of every later event, on a clean project. The read-and-append sequence (and the size-based rotation that can rename the file underneath it) now runs under an `O_EXCL` lockfile with a synchronous wait. A lock whose recorded pid is dead on this host, or that is older than 5s, is taken over; the 6s acquisition timeout deliberately exceeds that staleness window so an abandoned lock is always reclaimed rather than outliving every waiter. On a genuine timeout the event is still written — losing a security event is worse than a forked chain — but never silently: stderr names the lock, the holder's pid and host, and the wait. `O_EXCL` is atomic locally and not reliable on NFS, so a network-mounted home degrades to the age rule.
- An interrupted write no longer breaks the tamper-evident log for good. When the last line of `events.jsonl` was a torn append (a crash, a full disk or a kill mid-write), `writeEvent` could not parse it, restarted the chain at the genesis hash, and appended the new event onto the unterminated fragment. The new event was lost with the fragment, and every later event chained off genesis in the middle of the file, so `review` reported a critical `SHIELD-INT-002` and excluded every genuine event after the tear. The writer now links to the last valid event, skipping the torn line exactly as the reader does, and starts the new event on its own line. A line damaged between two events still breaks the chain through the next event's `prevHash`; only a trailing fragment is chained over, which is no more than truncating it already allowed. `opena2a shield selfcheck` now verifies the chain with the same reader and verifier `review` uses, so the two agree on whether the log is intact and where it breaks; it previously checked links only, missed content edits, and described every break as common and harmless. Its warning now states what `review` does with a break and names `opena2a shield recover --archive-log` as the way to start a fresh chain. Closes #244.
- `SHIELD-INT-002` (broken event-log hash chain) has a path to green. Its remediation was `opena2a shield selfcheck && opena2a shield recover --forensic`; followed verbatim on a broken log, selfcheck reported the config intact, `recover` reported "System is not in lockdown" (a chain break does not trigger lockdown), and `review` kept raising the critical. No command reset or rotated the event log, so the only exit was deleting `~/.opena2a/shield/events.jsonl` by hand — in a tamper-evidence system. New `opena2a shield recover --archive-log` refuses when the chain is intact, and otherwise renames the broken log to a timestamped `events-<ISO>.jsonl` sibling (the naming rotation already uses), starts a fresh genesis-anchored chain, and records the archive path, its sha256, the break index and the excluded-event count as that chain's first event. The log is archived, never deleted: it is the evidence, and anchoring its digest in the new chain means a break cannot be laundered by rotating it away. The remediation string now names this command.
- `opena2a mcp sign`, `verify` and `audit` accept the server as `--server <name>` as well as the positional. `mcp sign --server X` failed with `too many arguments for 'mcp'. Expected 2 arguments but got 3`: `mcp` allows unknown options, so `--server` was skipped and `X` became a third positional. Naming two different servers, one each way, exits 1. The per-subcommand help lists the flag. Closes #344.
- `opena2a rollback` and `opena2a fix-all` are registered. `secure --fix` printed "Run `opena2a rollback <dir>` to undo all changes" right after writing to the user's tree, and "Run `opena2a fix-all` to apply all available fixes", but neither verb was registered, so both answered `unknown command`. `opena2a-cli` installs one bin, so the `hackmyagent` form was not on PATH either. `fix-all --with-aim` (cited in the signing findings) fell into the natural-language matcher and exited 0 as `opena2a identity`. Both verbs now forward to the bundled scanner under its environment contract, the same as `secure`, and the citation rewriter maps `hackmyagent rollback` / `hackmyagent fix-all` to them. A new test runs `secure --fix` through the built CLI, requires every `opena2a <verb>` in its output to be a registered command, then runs the cited `opena2a rollback .` and checks the file comes back byte-identical. Closes #269.
- `opena2a shield init <dir>` hardens `<dir>` (#268). The positional was discarded, so run from another directory it wrote `arp.yaml`, `.opena2a/`, `.claude/settings.json` and `CLAUDE.md` into the current directory, signed that directory's `package.json`, and reported success for the target it never touched. The positional now works like `--dir`; two different directories, more than one positional, or a path that is not a directory exit 1 with the command that fixes it, before anything is written.
- `@opena2a/contribute`: `flush(url, verbose)` names the cause on stderr when the Registry cannot be reached, where it returned `false` silently; `submitBatch(null)` or an empty batch makes no request and resolves `false`, where it POSTed and resolved `true`; the abort timer is cleared on every path, so a failed request no longer holds the process open for up to 10s; and `flush()`'s return value is documented (`true` when the queue is clear afterwards, `false` when the events stay queued) (#299).
- `opena2a config set contribute false`, the form the ai-trust README and the website docs print, works. It answered `Unknown config action: set` and exited 1. `config set <contribute|llm> <value>` now does what `config contribute <value>` and `config llm <value>` do, and both forms accept `on`/`off` and `true`/`false` (plus `enable`/`disable`, `yes`/`no`, `1`/`0`). A value that is none of these now exits 1 and names the accepted values. Before, `config contribute banana` printed the current status and exited 0, which reads as success. The handler moved from `index.ts` to `commands/config.ts`, and its tests run against an isolated `$HOME`. Closes #343.
- Shield now reads its event log in fixed chunks instead of as one string, so a log of any size gets the verdict its content warrants. A log whose text reached 536,870,888 characters (the longest string Node can create, about 512 MB) could not be decoded: `opena2a review` and `opena2a shield log` read it as empty with an intact hash chain, `opena2a shield selfcheck` failed with `Failed to read events file.`, and `opena2a shield recover --archive-log` refused a broken log as intact. Shield's own writer rotates the log at 10 MB, so only a log written or extended by something else reached that size. Lines are now decoded across chunk edges and checked against the hash chain one at a time, only the events a command asks for are kept, and the sha256 that `recover --archive-log` records for the archived log is computed in chunks too. A single line too long to parse is skipped as an unreadable line, as an unparseable line always was.
- `opena2a review` no longer ignores an output option it was given. `--format json --report <path>` wrote nothing at that path and said nothing, because the JSON branch returned before the report was written; it now writes the HTML report there (owner-only, `0600`, when created), names the path on stderr, and keeps stdout pure JSON. `--format sarif` printed text, wrote the HTML report and exited 0, so a SARIF consumer received neither SARIF nor an error; review produces no SARIF, so any `--format` other than `text` or `json` now exits 2 before any check runs, with a message naming the two formats it supports. One exit code of a `--format json` run changes with this: a `--report` path that cannot be written (a missing directory, a read-only location) used to be ignored like any other, and the run exited 0 or 1 by score; it now prints the JSON report on stdout as before, names the cause on stderr as `Report not written: ...`, and exits 2, the same code as an unsupported `--format`, so a gate can tell an output that was not produced from a score below 50 (exit 1). A `text` run given such a path now exits 2 as well (#383).
- `opena2a guard sign` no longer records the operator's username or signs git-ignored files by default. `signedBy` is now `opena2a-cli/<version>` instead of `<os-username>@opena2a-cli`, so a signature store committed to a public repository no longer publishes the author's operating-system username. Existing stores keep their old value until `opena2a guard sign` is run again; `opena2a guard resign` re-signs changed entries in place and does not remove any. The default signing set, which `guard sign`, `guard verify`'s unsigned scan, `guard policy` and the signing `protect` does all share, now skips files git reports as ignored. An entry for a file the repository cannot contain, such as a local `.claude/settings.json`, failed `guard verify` as MISSING in every fresh checkout, including CI. The skip is never silent: text output names each skipped file with the ignore rule that matched, and `--format json` always carries a `skipped` array, empty when nothing was skipped. `--files <path>` still signs an ignored file on purpose, and tracked files are never skipped. `guard verify`'s summary line now includes the missing count, a MISSING row names its fix (restore the file, or run `opena2a guard sign` to rebuild the store), and a store with a `version` above 1 is refused as written by a newer opena2a-cli instead of being misread.
- `opena2a guard resign` and `opena2a admin sensors approve` and `reject` accept a typed `y`. Their confirmation prompts closed the input before recording the answer, so every answer, `y` and `yes` included, was read as a decline and the command was cancelled. Both prompts now use one shared confirmation that records the answer first. `admin sensors` still refuses to run non-interactively without `--yes`.
- `opena2a shield status` and the Integrity card in `opena2a review` now report the integrity state `opena2a shield selfcheck` computes. Status started at `HEALTHY` and changed it only when the lockdown marker existed, without running any check: on a tampered policy, selfcheck exited 1 with `COMPROMISED` while status printed `Integrity: HEALTHY` and exited 0, and on a log whose hash chain is broken status printed `HEALTHY` over selfcheck's `DEGRADED`. Both now take the verdict from the checks selfcheck runs, with the same shell. A `DEGRADED` or `COMPROMISED` state recommends `opena2a shield selfcheck`, a recommendation that could not fire before. When a check cannot run, status prints `Integrity: NOT CHECKED` with the same command instead of a default, and `--format json` carries `"integrityStatus": "not-checked"`. Status stays informational: it still exits 1 only while the lockdown marker exists.
- `opena2a shield recover --archive-log` no longer reports an event log it cannot read as intact. When `events.jsonl` existed but could not be read (for example a directory in its place), the command refused with `Event log hash chain is intact. Nothing to archive.` and `"status": "chain_intact"`, a claim it had not checked. It now refuses with `Event log could not be read, so its hash chain was not checked. Nothing archived.`, the read error, and `opena2a shield selfcheck` to inspect it; `--format json` reports `"status": "unreadable"` with the error in `error`. In both modes the read error is printed on one line with control and format characters removed and cut at 300 characters. The exit code stays 1 and nothing is archived. The chain check before archiving also no longer holds the log's events in memory: it read every event of the log into memory to compute three counts, and now counts them in the same fixed-chunk pass selfcheck uses, which keeps at most one event, the first one past the break, however long the log is.
- `opena2a review` honours the global `--quiet`. It printed the banner, six progress lines and the Observations block exactly as without it. With `--quiet` it now prints the score, the finding counts and the report path, plus one line giving the number of excluded Shield events when the event log hash chain is broken. The notices that qualify the verdict (deep scan did not run, event log chain broken) still go to stderr, and the contribute prompt is not shown. Under `--format json` stdout is unchanged and the `Report: <path>` confirmation on stderr is dropped. `--quiet` together with `--verbose` asks for opposite output, so it now exits 2 before any check runs, naming both options. Exit codes are otherwise unchanged.
- `opena2a shield suggest`, `explain`, `triage` and `monitor` now read the event log through the hash-chain check that `review` and `selfcheck` use. They read the raw log, so a line appended without recomputing the chain reached the LLM prompt, the policy suggestion, the incident triage and the ARP counts as if it were a recorded event. An event at or after a chain break is no longer sent to the LLM or counted. `suggest` and `triage` leave it out and print where the chain breaks, how many events are unverified, and the commands to inspect the log (`opena2a shield selfcheck`) and start a fresh chain (`opena2a shield recover --archive-log`). `explain` keeps the same events in its window but marks each one past the break `UNVERIFIED` and does not explain it. `monitor` does not count it, and reports an ARP event whose only record is past the break as recorded only past a chain break instead of already imported; after the archive, the next `monitor` run imports it into the fresh chain. With `--format json`, `suggest`, `triage` and `monitor` add a `verification` object (`chainBroken`, `brokenAt`, `untrustedCount`), each `explain` result adds `verified`, and `monitor`'s `import` object adds `skippedUnverified`.
- `opena2a shield log` now says which events it lists are past a break in the event log's hash chain. It read the raw log, so a line appended without recomputing the chain, or the events after a deleted line, were listed as ordinary events while `opena2a shield selfcheck` reported the break. The log still lists the same newest `--count` matching events, since it is the forensic view, but when the chain is broken it prints once where the chain breaks and how many events from there on are unverified, with the commands to inspect the log (`opena2a shield selfcheck`) and start a fresh chain (`opena2a shield recover --archive-log`), and marks each listed event past the break `UNVERIFIED`. An intact log prints as before. With `--format json` the output is still an array of events, and each event adds `verified` (`true` before the break, `false` at or after it). The exit code stays 0.
- `opena2a shield log` and `opena2a shield explain` print the event fields they list as plain text. The timestamp, severity, action, target and outcome were written to the terminal as recorded, so a line in the event log could carry an escape sequence that hid the text printed after it, including the `UNVERIFIED` marker, or a line break that printed a second, made-up row. Line breaks and other whitespace now print as spaces, and control and format characters are removed, as `recover --archive-log` already does for its read error (#389).
- `opena2a shield log` and `opena2a shield explain` no longer stop at an event whose `severity` is not a string. One such line made both commands print `Error: severity.toUpperCase is not a function` and exit 1; the event is now listed with its severity printed as JSON text, for example `[5]` (#389).
- `opena2a shield suggest --format json` and `opena2a shield triage --format json` print JSON on every path. When no event was found, when no verified event was found past a chain break, or when the LLM returned no result, they printed plain text, so the output did not parse. They now print `{"status": ..., "verification": {...}}` with `status` set to `no-events`, `no-verified-events` or `llm-unavailable`. `opena2a shield explain --format json` prints `[]` when no event matches, where it printed a text line. In text output, `suggest` and `triage` now print the chain-break notice when the LLM returns no result, where they printed only `LLM analysis unavailable.` (#389).
- `opena2a shield triage --severity <level>` triages events of that severity or above, as its messages (`No high+ severity events found.`) already said. It selected that severity only, so under the default `--severity high` a critical event was never triaged. A level outside `info`, `low`, `medium`, `high` and `critical` matches no event. `shield log` and `shield explain` still select exactly the severity given (#389).
- `opena2a shield report` computes its runtime-protection figures from the verified events it already reads, as `opena2a review` does. They came from a second read of the log without the hash-chain check, so one ARP line appended past a chain break marked ARP active and raised the posture score: measured on a log with one genuine Shield event, 60 (enforcement 20, coverage 20) became 73 (enforcement 50, coverage 40). An ARP event past a break no longer changes the score, the factors or the HTML report's runtime-protection section (#389).
- `opena2a identity attach` and `opena2a identity sync` import Shield events into the AIM audit log through the hash-chain check. They parsed the event log line by line, so an event past a chain break was recorded in the audit log as a Shield event. It is now left out; when any were, both commands print how many Shield events were left out, with `opena2a shield selfcheck` to inspect the log and `opena2a shield recover --archive-log` to start a fresh chain, and with `--format json` `identity sync` adds `unverified` and `identity attach` adds `unverified` to `bridgeResults` (#389).
- `opena2a shield monitor` says how many ARP events a chain break holds back. It counts verified ARP events only, so one line appended without recomputing the chain removed every later ARP event from the Runtime Protection Summary and Detections without saying how many. It now prints the number of ARP events past the break in the period, with their anomaly, violation and threat counts, under `Unverified, not counted`; they are still not added to the summary. With `--format json` the output adds `unverifiedStats` (#389).

### Security
- **`opena2a review` no longer writes detected credential values into its reports.** `credentialData.matches[].value` carried each detected secret verbatim, in `--json` output and in the payload embedded in the HTML report, while the HTML page itself showed a masked preview. The HTML report is written owner-only (`0600`) when it is created (#267).
- **Every child process opena2a-cli starts now receives a declared environment, never the operator's whole one.** Seven sites in shipped code spread `process.env` into a child: `packages/cli/src/index.ts` (the two direct `hackmyagent` spawns), `router.ts` (the `check` delegation), `shield/llm-backend.ts` (the `claude --print` call), and the `envInherit` branch of `adapters/spawn.ts`, `python.ts` and `docker.ts`. `commands/review.ts` passed no environment at all to its `npx hackmyagent secure`, which inherits the same way. The children are the delegated scanner and the local model CLI binary. Every release since each site appeared handed that child the operator's full environment — cloud credentials, registry tokens, database URLs, every API key in the shell — and 0.10.12, which narrowed the adapters' allowlisted path, recorded that these direct spawns still inherited. The history available for this entry is the release notes, which name a site only when a release changed it: the adapters and the model-CLI backend are first recorded in 0.1.2, `review` in 0.3.1, and the `check` delegation in 0.5.0, where it appears as a fix and so had already shipped; a site may predate the note that first mentions it. What each child receives is now declared once per binary in `CHILD_ENV_CONTRACTS` (`adapters/registry.ts`) and resolved by one function, `childEnv(binary)`, so every route to a binary hands it the same environment and a binary with no declaration fails loudly rather than inheriting. The scanner gets its existing contract on every route (`scan`, `check`, `review`, `scan-soul --explain`): `NANOMIND_URL`, `NANOMIND_GUARD_SOCK`, `ANTHROPIC_API_KEY`, `REGISTRY_URL`, `REGISTRY_API_KEY`, `ATC_TOKEN`, `INTERNAL_API_KEY`, `CI_SCAN_HMAC_SECRET`, `OPENA2A_REGISTRY_TOKEN`, `HMA_COMMUNITY_SECRET`, `HACKMYAGENT_LLM_BUDGET`, `HMA_EXPORT_TRAINING`, `HMA_INTEGRITY_DEBUG`, `ARP_TELEMETRY_DISABLED`, `AWS_REGION`, `AWS_ACCOUNT_ID`, `NODE_ENV`, `npm_config_key`, the `HMA_` prefix and the node-toolchain prefixes, plus the three `HMA_*` citation names the direct spawns set. ### Known issues
- **A second, deprecated copy of `hackmyagent` survives this release, and one command still reaches it.** The pin above moves the copy opena2a-cli itself loads. It does not move the copy nested under `ai-trust`, which arrives through `ai-trust`'s dependency range rather than ours: opena2a-cli declares `ai-trust: "^0.2.23"`, that caret resolves `ai-trust@0.2.25`, and `0.2.25` declares `hackmyagent: "^0.17.1"`. Every version published in that range is one we deprecated — `npm view 'hackmyagent@^0.17.1' deprecated` prints the same notice for all eleven of them — so which one npm picks for you does not change the finding, and this note deliberately does not name one. **Verify in your own tree:** `npm ls hackmyagent` lists every resolved copy and the dependency that pulled it in (add `-g` if you installed opena2a-cli globally), and `npm view hackmyagent@<the version it printed> deprecated` prints the notice for that copy. **What it affects:** `opena2a registry <package>` and `opena2a publish` reach it. Both route through the same adapter, which delegates to `ai-trust check`, and `ai-trust` resolves its own copy. `scan`, `review`, `check`, `scan-soul`, `harden-soul` and `benchmark` do not. **Fix:** npm honours an `overrides` block only in the root `package.json` of a project, never one declared inside an installed dependency ([npm docs](https://docs.npmjs.com/cli/v11/configuring-npm/package-json#overrides)), which is why we cannot ship this fix and you can. Adding `"overrides": { "ai-trust": { "hackmyagent": "0.30.0" } }` to your own `package.json` and reinstalling collapses the two copies into a single non-deprecated `hackmyagent@0.30.0`; measured on 2026-08-11, `ai-trust check express` still runs and exits 0 under it. What that measurement does not cover is every `ai-trust` code path against a scanner outside its declared range, so treat it as a workaround to re-check after any `ai-trust` upgrade, not as a supported configuration. If you would rather not, run `hackmyagent check <package>` from a current `hackmyagent` and read that verdict instead. Upgrading `ai-trust` does not help on its own: `ai-trust@0.7.6`, the current release, pins `hackmyagent 0.23.11`, which carries the same deprecation notice. The durable fix is an `ai-trust` release that admits a non-deprecated `hackmyagent`, and `npm view ai-trust dependencies.hackmyagent` is the one-line check that tells you when that has happened.

### Fixed
- Scans are scoped to what you asked them to scan, and credentials are caught whatever shape the key is. Both fixes live in the pinned scanner and land here with the `hackmyagent` pin moving 0.25.1 -> 0.25.2 (exact), which this release carries. `secure`/`scan`/`review` were folding findings from the AI runtimes installed in `$HOME` — `~/.openclaw`, `~/.nemoclaw` and peers — into the score for whatever directory you pointed them at. Measured on a machine with a populated `~/.openclaw`: `opena2a review <an empty directory>` reported **0/100 and 1782 findings**, opening "Not safe to ship. [OpenClaw] Browser Data Access + 1781 more", where the same directory under a sandboxed `HOME` scored 98 with 1 finding. `--fail-below` was therefore not a CI gate: the identical commit scored 98 on a runner and 0 on a laptop. Those runtimes are now reported in their own labelled section — name, path and a runnable command that scans that scope — and are never scanned here, never counted in the target's findings, score or exit code, and carry no score of their own. Separately, `opena2a scan` returned **98/100 and exit 0** on a source file holding a hardcoded legacy `sk-` key while returning 69/100 and exit 1 on the same file using a `sk-proj-` key. The scanner adds the one missing pattern (`sk-[a-zA-Z0-9]{48,}`) and anchors every existing one so a vendor prefix glued to an identifier tail no longer matches — `disk-<sha256>` had read as an OpenAI key. See the hackmyagent 0.25.2 notes for why the fix is deliberately limited to that shape.
- The CLI points at one registry, and it is one that resolves. `opena2a config show` reported `https://registry.opena2a.org` on a fresh install and `opena2a trust <pkg>` failed with "fetch failed", while `scan --help` advertised `https://api.oa2a.org` — two conflicting defaults in one CLI. That hostname has no DNS deliberately: it names the unreleased Registry frontend, not the API. The cause was a stale dependency pin — `@opena2a/shared` at 0.1.0 shipped the dead host as its built-in default and carried no migration — so the value was always present and always wrong. The pin moves to 0.1.2 and the registry URL is now resolved in one place: unset, blank, and every known stale host all resolve to `https://api.oa2a.org`, while a deliberately configured self-hosted registry is left alone. `trust`, `claim`, `mcp-audit` and `detect` all route through it and no longer carry private default constants; `admin` keeps its own on purpose, because it transmits the internal admin key and must never follow ambient config.

  **One behaviour change worth stating plainly:** if you have opted into community contributions, reports that previously failed to leave your machine now arrive. Nothing about consent changed — every submission path was, and still is, gated on `isContributeEnabled()` before the URL is ever resolved — but the URL those consented submissions were being sent to did not exist, so they silently failed at the network layer. They now reach `https://api.oa2a.org`. If that is not what you want, `opena2a config contribute off`.
- Two different measurements no longer share one name. `review` computed a Shield runtime posture (active tools, policy, shell integration, penalized by findings) and `init` computed a project governance posture; both were called `postureScore` and both rendered under the label "Posture Score", so one report showed 52 on the Overview page and 35 on the Shield page with nothing saying they measured different things. - `comply` no longer reports a bare `process.env.X` reference as a CREDENTIAL violation (#254). The generic keyword rule in `@opena2a/aicomply` captured the 26-character accessor `process.env.OPENAI_API_KEY` as the secret, because `apiKey` satisfies `/api[_-]?key/i` and the value character class contained `.`; the masked preview `pro****EY` was that string, not a key. This is the shape `protect` rewrites a hardcoded key *into*, so a user who followed the remediation and then ran `comply` as a CI gate got a VIOLATION on correctly-fixed code, and two commands in the same CLI disagreed about whether best practice is a violation. Fixed upstream and shipped: the pinned `@opena2a/aicomply` moves 2.2.0 -> 2.2.3 (exact). That release also stops an empty-valued key adopting the next line as its secret, which had produced a false CREDENTIAL on `.env.example` files — verified downstream here as well.
- `protect` no longer exits 0 after a non-interactive run that changed nothing (#256). `opena2a protect < /dev/null` printed the credential table, printed the raw confirmation prompt, and exited 0 with the credential still in source: the prompt rejects at EOF and the catch treated that as "no". Exit 0 is an affirmative claim, so a pipeline checking the exit code concluded the migration had happened. A non-TTY stdin is now detected before prompting; protect exits 2 and names `--ci` and `--dry-run`. A prompt that throws mid-run also exits 2, because no decision was reached. A deliberate "n" still exits 0 — the user was asked and answered. The gate sits above the output-format branch, so `--format json` is no longer a consent bypass: previously `opena2a --format json protect` with stdin closed rewrote source files, moved secrets into the vault, edited `.gitignore` and signed configs without ever asking, because the confirmation was skipped entirely in JSON mode. It now returns the same refusal as `code: CONFIRMATION_REQUIRED`. `--ci` was reachable only as a global option and never appeared in `protect --help`; it is now registered on the command, and either placement works.

  Note for automation: a bare non-interactive `opena2a protect` changes from exit 0 to exit 2. That is the point of the fix — exit 0 was an affirmative claim about work that never ran — but any pipeline relying on the old behavior must add `--ci` (to migrate) or `--dry-run` (to preview). No in-repo caller depends on protect's exit code.
- `protect`'s rollback guidance is runnable where it is printed (#257). The sole advertised undo was `git checkout -- <files>`, printed unconditionally — including in a `mktemp -d` with no repository, where it cannot run, and there is no `--undo` flag to fall back on. Rollback rendering now asks git whether the target is inside a work tree (via `rev-parse`, so a subdirectory of a repo still qualifies) and only offers `git checkout` there. Outside a repo it states that the source edit is not reversible from disk and names `npx secretless-ai secret list` / `secret get <NAME>`, verified subcommands of the vault protect writes to. Deliberately not a rollback manifest: the original file still holds the plaintext credential, so a backup on disk would re-create the exposure protect had just removed.
- Both halves of an AWS key pair are judged by one rule (#258). AWS's published documentation pair produced exactly one finding — DRIFT-002 on the access key id, nothing on the secret — so a user acting on the output migrated the harmless identifier and left the dangerous value in place. Re-running the same file shape with a non-example 40-char secret produced both findings, which establishes that CRED-005's pattern was never broken: suppression ran only for `nameGated` patterns, and CRED-005 is name-gated while DRIFT-002 is not. Prefix-bearing patterns now suppress on EXACT membership in the canonical `@opena2a/credential-patterns` `KNOWN_EXAMPLE_KEYS`, which lists both halves of the AWS pair source-verified against the IAM User Guide. Deliberately exact and not a substring test: every prefix-bearing pattern admits `_`/`-` in its body, so a substring rule would let `<live key>-SAMPLE` match greedily, contain a placeholder word, and be dropped — while `.replace('-SAMPLE','')` restores the key at runtime. It would also blank the project's own malicious corpus, whose fixture credentials are deliberately marked `FAKE`, and disagree with `hackmyagent` on the same bytes. Name-gated patterns keep the broader placeholder + entropy guard, because their match rests on a nearby name rather than the value's shape. Both duplicated match loops now call one predicate, so `init` and `protect` cannot drift on what counts as a credential.
- `shield evaluate` reports a verdict in its default text mode (#255). It wrote zero bytes and exited 0, which is indistinguishable from a crash, while `--json` proved the work had happened. The silence protected the shell preexec hook, which runs `evaluate` on every interactive command; that is preserved, because the installed hook always passes the command as a positional argument and never passes `--action`/`--target`. Hook mode is keyed off the raw arguments rather than the parsed command string, so an absolute-path command is not misread as a direct invocation. `--action` and `--target` are now registered options: they are printed as remediation by the Shield findings themselves, but `allowUnknownOption` silently swallowed them, so the evaluated target was always the empty string and the run printed nothing — following the tool's own advice reproduced the bug it was meant to fix. The verdict names the outcome, deciding rule, agent, and the subject actually evaluated, and states a default-allow out loud rather than implying the action was vetted.
- `skill create` generates a skill that passes `scan` (#259). `skill create` → `scan` is the documented quickstart, and it reported the tool's own pristine output as `malicious` with 5 HIGH findings. Measured against hackmyagent 0.25.1: 55/100 · 5 high · `malicious` → 69/100 · 1 high · `unknown`. SKILL.md now carries inline Trust Hierarchy and Constraints sections (the prompt-security checks read the artifact's own constraints, so a sibling SOUL.md would not have satisfied them); the `heartbeat:` frontmatter block is gone, because SKILL-003 matches it per-line and the schedule already lives in HEARTBEAT.md; HEARTBEAT.md declares `activeHours:`; and the scaffold ships a `.gitignore` that does not ignore `.env.example`. The remaining findings all require an AIM identity, a verified publisher, or a registry submission and cannot be satisfied by generated files. `skill create` also no longer claims "Signed SKILL.md and HEARTBEAT.md" when what it wrote is an opena2a-guard pinned hash — it says so, and names `hackmyagent fix-all --with-aim` as the way to get an AIM signature.

### Security
- `self-register` no longer writes to the public registry without consent. The command submits community scan-result records to `api.oa2a.org`; `--dry-run` existed but the destructive path was the default and nothing was asked before it ran. A release-test harness invoking the bare command published records from a developer laptop — a sandboxed `HOME` did not prevent it, and `OPENA2A_TELEMETRY_URL` does not apply because `self-register` talks to the registry directly. It now confirms interactively, and a non-interactive shell (`--ci`, or any pipe where stdin is not a TTY) must pass `--yes`. The refusal exits 2 and names both `--yes` and `--dry-run`, in text and in JSON (`code: CONFIRMATION_REQUIRED`), so an automated caller relying on the old behavior fails visibly rather than silently doing nothing. The gate sits ahead of the per-tool loop, so a refused run performs no existence checks and no HMA scans — previously a bare invocation made 33 requests before finishing.

## [0.10.12] - 2026-07-29

### Security
- Delegated tools now receive an allowlisted environment declared by their own adapter registry entry, instead of the operator's entire environment (#228). Measured on one developer machine: 128 variables reached the child, 11 of them credentials; now 20 and none. The contract lives on each `ADAPTER_REGISTRY` entry (`envAllow` / `envAllowPrefixes`) rather than in a single generic list, because these adapters run first-party tools with real environment contracts — `secretless-ai` needs `VAULT_ADDR`/`VAULT_TOKEN`/`AWS_*` because it is a credential broker, and `hackmyagent` needs `NANOMIND_URL`/`NANOMIND_GUARD_SOCK`/`ANTHROPIC_API_KEY` or it silently returns different findings with a zero exit code. Both reach the spawn path through the import-adapter fallback. New `util/child-env.ts` supplies the base allowlist (PATH/HOME/locale, proxy and custom-CA settings, CI markers, telemetry opt-out, the `*_CLI_PREFIX` citation vars) and a credential-name guard over prefix matches; exact entries bypass the guard, which is how a tool declares the credential it genuinely uses and how `SECRETLESS_CLI_PREFIX` survives a substring match on "secret". Availability probes (`which x`, `x --version`, `python -c "import m"`) get a narrower probe environment with no credentials at all. Operators can extend the allowlist with `OPENA2A_CHILD_ENV_ALLOW="NAME,PREFIX_*"`; a bare `*` and any prefix under three characters are refused, entries are capped, the widening is reported on stderr, and the variable is never forwarded to the child. The `release-smoke-comply` and `release-smoke-init` harnesses use the same mechanism. `secrets` and `broker` are declared EXEMPT (`envInherit`) rather than allowlisted: `secretless-ai` reads credential names it discovers at runtime, so a static list made `opena2a secrets verify` report a different machine than `secretless-ai verify` with both exiting 0. Their availability probes stay narrow regardless. The direct `hackmyagent` spawns in `router.ts`/`index.ts`/`review.ts`, `shield/llm-backend`, and the corpus parity harness still inherit the full environment and are tracked in #246. Scope note: this reduces environment-borne exposure only — `HOME` is forwarded by design, so `~/.npmrc`, `~/.aws/credentials` and `~/.docker/config.json` remain reachable by any child, and the guard matches names, not values.
- `shield recover --verify` now verifies before it recovers, which is what the flag has always claimed (#228). A `degraded` result still unlocks — a missing shell rc file must not strand anyone — but it no longer reports "successful verification"; the warnings are named in both the text and JSON output. Note `enterLockdown` has no production caller today, so this closes a fail-open on a path the shipped CLI does not currently reach. It previously called `exitLockdown()` first and re-entered lockdown only if the checks came back compromised, because `runIntegrityChecks` short-circuits while the lockdown marker is present. That briefly unlocked a compromised machine, and a check that threw — or a SIGINT, or a kill — during the window left it unlocked permanently. `runIntegrityChecks` takes a new `ignoreLockdown` option so the battery can run with the marker still in place; every other caller keeps the short-circuit.

### Fixed
- `benchmark` no longer certifies controls it never evaluated (#250). It returned `Certified`, `L1: 100% (39/39)` for an empty directory and for a project with a hardcoded API key, because a control counted as passing whenever no finding mentioned its check id — and the only source consulted evaluates none of the 39 OASB L1 controls. Scoring is now coverage-gated: unevaluated controls leave both sides of the ratio and are disclosed by count on the score line and by id under `--verbose`; `Certified`/`Passing` require complete coverage; zero coverage reports `Not assessable`. Credential controls are genuinely evaluated via the same scanner `init` and `protect` use, so `protect` and `benchmark` now agree that a hardcoded key fails CRED-002. Categories with no controls at the requested level report `n/a` rather than `0%`. New `npm run release-smoke:benchmark` corpus-tier gate.
- Every score line now states its scope (#252). `init`, `scan`, `review` and `benchmark` measure different things, and four bare numbers for one directory read as a contradiction. `init` labels project posture; `review` labels the composite and says when a critical dimension capped it rather than an average producing it; `benchmark` states evaluated-vs-total coverage.
- `init` detects credential-shaped values in template env files (#227).
- `review`'s verdict line no longer disagrees with the composite band it reports (#221, #222).
- Telemetry is suppressed in CI and under `DO_NOT_TRACK` (#240); the SDK's default endpoint points at the canonical ingest path (#225).

### Changed
- `hackmyagent` pin 0.23.6 -> 0.25.1 (#229, #239, and this release). 0.10.11 shipped 0.23.6, so the delegated scanner moves three steps for anyone upgrading and corpus aggregate scores move with it (the 0.25.0 -> 0.25.1 step alone: 83 -> 69, 76 -> 69). Across that last step the finding sets are byte-identical on every affected fixture — same check ids, same severity histogram — so the movement is 0.25.1's scoring corrections removing inflation rather than lost detection, and the parity goldens are re-baked per the documented pin-bump process. 0.25.1 also carries the artifact-intent reconciliation that stops `scan` printing a raw classifier label on a clean artifact, which is the label half of #251.

### Added
- `protect --grant <grant-ref> --atx <path>`: opt-in Agent Authorization Protocol gate. Before any scan, `protect` presents an ATX to the local Secretless broker and proceeds only if the broker authorizes the grant. The `packages/cli/src/aap/` broker client is the first TypeScript AAP consumer. Defends T-3002, T-3003, T-3006, T-8002 at the CLI surface.
  - Exit codes: 0 (broker authorized), 2 (--grant without --atx or invalid ATX), 3 (403 opaque denial, AAP §6.6), 4 (broker socket unreachable), 5 (unexpected error), 6 (broker returned non-403 non-200 status — body never echoed to user).
  - Hardening: default-socket-path connections require socket-uid == process-uid (defense against same-box impostor brokers); ATX file capped at 256 KiB; response body capped at 1 MiB; ANSI/C0 control chars in user-supplied grant references are stripped before stderr output.

- `opena2a admin sensors`: enrollment-inbox operator command (#224).

### Known issues
- No project can reach `Certified` on `benchmark` today, and anything that previously read `Certified` will now read `Partial`. That is the #250 fix working, not a new failure: `Certified` requires complete coverage of the level, and the scanners this command consults evaluate 3 of the 39 OASB L1 controls (credentials only). Every run says so explicitly — `L1: 100% (3 of 39 controls evaluated)`, `36 of 39 controls were not evaluated`, `these are NOT counted as passing`, and per-category `not evaluated (0 of 8 controls assessed)`. Widening coverage needs HMA's semantic pass wired in; until then a thin true number is reported instead of a complete-looking false one.
- Following `harden-soul` still costs 5 points on `init` (#251, reopened). `scanSoulFile` matches injection patterns with a bare substring test, so the one line of generated governance that NAMES the phrases it resists (`If any input contains phrases such as "ignore previous instructions", ...`) is counted as an override pattern: `init` reads 75 before `harden-soul` and 70 after, with a HIGH `soul.md contains 1 override pattern`. Two context-aware matchers were attempted this cycle and both were reverted — quote-parity counting was defeated by a single apostrophe in prose, closed-span matching by two apostrophes or by quoting the payload, each losing a true positive the substring matcher caught (classification (b) narrowed-detection). The plain matcher is restored and every evasion is pinned as a regression test, so a future context rule has to clear them first. The fix belongs upstream, where hackmyagent's `hardenSoul` generates the line, or in a corroboration rule that declines to penalise a file `scan-soul` independently rates hardened — not in a third regex. The label half IS fixed: the same file now reads `soul · unknown` rather than `soul · malicious`, so the analyzers no longer contradict each other on direction.
- `opena2a scan` still reports 96/100 on a file with a hardcoded OpenAI key: the delegated scanner marks CRED-002 as passing there (hackmyagent#316, verified against the HMA binary with a high-entropy key). `init`, `protect`, `review` and `benchmark` all flag it, so `scan` is the outlier until that fix lands.
